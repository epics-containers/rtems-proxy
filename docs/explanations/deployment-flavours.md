# Three flavours of RTEMS IOC

As we transition to RTEMS there are three ways in which RTEMS IOCs are
deployed. Which one applies to you depends on how the existing IOC was built.

## 1. Fully containerised with ibek

The end goal: all IOCs are eventually done this way.

The RTEMS IOC is cross compiled inside the container build and becomes part of
the [Generic IOC](https://epics-containers.github.io/main/explanations/introduction.html#generic-iocs-and-instances)
container image. The build happens in CI and the image is published to a
registry — exactly the workflow used for Linux soft IOCs.

At build time:

- define the Generic IOC exactly as you would for a Linux Generic IOC;
- use the `ansible.sh` script to fetch and build the required support modules;
- the only difference is that `ARCH` is set to `RTEMS-beatnik` in the CI build,
  e.g. see [ioc-dlsvmevac CI](https://gitlab.diamond.ac.uk/controls/containers/iocs/ioc-dlsvmevac/-/blob/2025.5.1/.gitlab-ci.yml?ref_type=tags#L41-43);
- tagging a release builds and publishes an image, just like a soft IOC.

At runtime the binary is extracted from the container and served to the target
over TFTP; protocol files are extracted and served over NFSv2; `st.cmd` and the
database are generated by ibek from an `ioc.yaml`; and the proxy container
drives the crate over telnet.

Example Generic IOC: [ioc-dlsvmevac](https://gitlab.diamond.ac.uk/controls/containers/iocs/ioc-dlsvmevac/-/tree/2025.5.1?ref_type=tags).
Example instance: [bl04i-va-ioc-01](https://gitlab.diamond.ac.uk/controls/containers/beamline/i04-services/-/tree/main/services/bl04i-va-ioc-01).

**Status:** proven, and the example above has been tested on I04. However it
was implemented using RTEMS6, and for the moment we are targeting RTEMS5. For
the RTEMS5 rollout, use one of the two interim approaches below.

## 2. Containerised proxy with manual RTEMS IOC management

An interim step for **non-builder** VxWorks IOCs. The IOC is manually ported to
RTEMS and released to `/dls_sw/prod` by the build server.

The changes required are:

- update to EPICS v7;
- change the `src/Makefile` target to the generic name `PROD_IOC = ioc` (and
  rename `xxxMain.cpp` to `iocMain.cpp`) so the build emits
  `bin/RTEMS-beatnik/ioc.boot` — rtems-proxy expects this generic boot name,
  not one derived from the IOC instance;
- use support module versions/branches that support RTEMS5;
- rewrite the startup script to be compatible with RTEMS5;
- release to prod using `dls-release`.

For more on the porting process see
[converting to RTEMS](https://confluence.diamond.ac.uk/x/_w6WFQ),
[general RTEMS info](https://confluence.diamond.ac.uk/x/s50AC), and the
`#rtems6` slack channel.

Example IOC: [bl06i-mo-ioc-02](https://gitlab.diamond.ac.uk/controls/containers/iocs/ioc-bl06i-mo-02).
Example proxy instance: [bl06i-mo-ioc-02](https://gitlab.diamond.ac.uk/controls/containers/beamline/i06-services/-/tree/main/services/bl06i-mo-ioc-02).

## 3. Build server and ibek — hybrid

The quickest route onto RTEMS5 if your existing IOC uses XmlBuilder:

- use a Generic binary pre-built for e.g. beamline vacuum;
- use an auto-converted `ioc.yaml` so ibek generates the startup script and
  database;
- still pull all the DB templates from `/dls_sw/prod`.

This is the approach most of these docs are about — see
[](./hybrid-mode.md) for how it works, and
[](../tutorials/hybrid-ioc-walkthrough.md) for a worked example.
